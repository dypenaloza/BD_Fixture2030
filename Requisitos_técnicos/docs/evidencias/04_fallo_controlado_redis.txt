Interpretación: la API no devolvió un 500 genérico ni colgó el request;
tradujo la caída de la dependencia en un 503 con código identificable
(REDIS_UNAVAILABLE), con request ID para correlacionar con el log.

--- 4. Recuperación del servicio ---
Comando: docker start fixture2030-redis
Estado del contenedor: running

{"usuarioId":"U27961","nombre":"Bruno","rol":"fan","ultimoAcceso":"2030-06-13T19:48:00Z","partidoSiguiendo":"P-R32-6","ttlSegundos":1758}

2026-10-23 17:16:23,397 | INFO | RequestID=816a3f58-8492-477b-8092-a9f009a1fd62 | Metodo=GET | Ruta=/sesiones/{usuario_id} | Fuente=Redis | Estado=200 | Duracion=4.54 ms

Interpretación: el pool de conexiones de redis-py (cacheado con
lru_cache en el adaptador, ver API_REST/docs/arquitectura_y_adaptadores.md

de la API. Esto es consistente con el comportamiento documentado para
Mongo/Neo4j/Cassandra/Redis (a diferencia de IRIS, que no usa pool y
abre una conexión nueva por consulta).

--- 6. Datos conservados ---
La sesión de prueba (sesion:U27961) siguió existiendo con el mismo
contenido antes y después de la caída. El TTL bajó de forma continua
(1775s -> 1758s, ~17s transcurridos entre ambas lecturas), confirmando
que Redis no se reinició desde cero ni perdió el dato: solo el proceso
estuvo detenido, nunca se tocó el volumen.
